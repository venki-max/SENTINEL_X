1.Executive Summary

SENTINEL-X 2.0 is a full-stack cybersecurity web application developed as a second-year Cyber Security academic project. It provides a unified Security Operations Centre (SOC) interface that allows analysts to investigate suspicious Indicators of Compromise (IoCs) — including IP addresses, domains, URLs, and file hashes — by querying multiple external threat intelligence sources, correlating their findings, and generating explainable risk scores with concrete analyst recommendations.

The platform demonstrates practical application of threat intelligence concepts including multi-source correlation, explainable AI-style scoring, SSRF protection, audit logging, and structured evidence management. It ships with 20 pre-loaded demo investigation scenarios covering all risk classifications and indicator types, and is fully demonstrable in a college environment without any external API keys.

2.Problem Statement

Modern organisations face a continuous flood of potential cyber threats. Security analysts must frequently determine whether a given IP address, domain, URL, or file hash is malicious — but the available intelligence is scattered across multiple providers, often contradictory, and delivered without actionable context.

Existing limitations in freely available tools:

  • Single-source lookups provide no cross-validation — a clean result from one source may be flagged by another.
  • Raw API responses require significant analyst expertise to interpret without additional tooling.
  • No open-source platform explicitly surfaces conflicts between intelligence sources with explanations.
  • Risk scores, where they exist, are opaque — analysts cannot see why a score was assigned.
  • Case management is entirely separate from investigation workflows in most free tools.
  • Demonstration and training are impossible when external APIs are unavailable or rate-limited.

SENTINEL-X 2.0 addresses all of these gaps in a single, locally deployable, open-source platform.

4.System Architecture

SENTINEL-X 2.0 follows a standard three-tier web architecture. The React SPA is served as static files by Flask, making it a single-process deployment. The frontend communicates with the backend exclusively through a documented REST API, with all external provider queries handled server-side to protect API keys and prevent SSRF attacks.

Investigation Data Flow

1.  Analyst submits indicator value (IP / domain / URL / hash)
2.  Input validation  →  max 2048 chars, non-empty
3.  Type detection    →  ipaddress module + regex patterns
4.  SSRF check        →  private/loopback/link-local IPs blocked
5.  Normalisation     →  canonical form (lowercase, compressed IPv6, etc.)
6.  Provider queries  →  VirusTotal API  +  AlienVault OTX API  (parallel)
7.  Normalisation     →  provider responses → common EvidenceItem format
8.  Correlation       →  agreement / conflict / missing detection
9.  Risk scoring      →  weighted 0-100 score + contributing factors
10. Recommendation    →  rule-based action list per risk class + itype
11. Persistence       →  Investigation + SourceResults + EvidenceItems + Snapshot
12. JSON response     →  frontend renders all result panels

6.Database Design

The database consists of 12 SQLAlchemy ORM models. The Investigation model is the central entity, linking an Indicator (the IoC being examined) to provider results, evidence items, and snapshots. Cases provide a management layer that groups multiple indicators and investigations together.

ModelPrimary KeyKey FieldsPurpose
UserIntegerusername, email, password_hash, roleAnalyst accounts (admin / analyst roles)
IndicatorIntegervalue, itype, normalized, first_seen, last_seen, is_demoCanonical record of a unique IoC
InvestigationUUID Stringindicator_id, risk_score, risk_class, summary, data_source, is_demoOne investigation run linked to an indicator
SourceResultIntegerinvestigation_id, provider, status, raw_response, normalizedPer-provider raw and normalised response (JSON)
EvidenceItemUUID Stringinvestigation_id, provider, evidence_type, value, confidenceIndividual evidence facts extracted from responses
IndicatorRelationshipIntegersource_id, target_id, rel_type, provider, confidence, evidence_refDirected edges in the relationship graph
CaseUUID Stringtitle, severity, status, assigned_to, created_by, is_demoInvestigation case container
CaseIndicatorIntegercase_id, indicator_id, added_by, added_atMany-to-many: cases ↔ indicators
AnalystNoteIntegercase_id, author_id, content, created_atFree-text analyst notes attached to cases
ActivityEventIntegercase_id, user_id, action, detail, timestampAudit trail — all case state changes and actions
ReportMetadataUUID Stringinvestigation_id, report_format, generated_by, generated_atRecord of exported investigation reports
InvestigationSnapshotIntegerinvestigation_id, snapshot_data (JSON), taken_atPoint-in-time copy for change comparison
All timestamps are stored in UTC. Investigations and Cases use UUID string primary keys. A unique constraint on (value, itype) prevents duplicate indicator records. No API secrets are stored in the database — all provider keys remain in environment variables.

7.2 Interactive Relationship Graph

The Graph page uses React Flow v11 to render an interactive node-edge canvas. Nodes are colour-coded by indicator type, edges carry relationship type labels and provider attribution. High-confidence edges (confidence > 0.7) are animated with a dashed stroke. Users can zoom, pan, drag nodes, and view the minimap. The graph is populated from IndicatorRelationship records stored in the database.

7.3 Case Management

Cases support five statuses: New Investigating Escalated Resolved Closed. Each case tracks: linked indicators, analyst notes with author and timestamp, severity level, assigned analyst, and a full chronological activity timeline. All status changes are written to the ActivityEvent audit table with actor and timestamp.

7.4 JSON Report Export

Every investigation can be downloaded as a structured JSON report (GET /api/reports/{id}/json). Reports contain: unique report ID, investigation ID, indicator details, UTC timestamps, risk assessment, source-by-source normalised results, evidence items with confidence scores, correlation findings, analyst recommendations, data provenance label, and a legal notice clarifying evidentiary limitations.

7.5 Investigation Change Monitor

Every investigation automatically saves an InvestigationSnapshot at creation time. The GET /api/investigations/{id}/compare endpoint compares the two most recent snapshots, returning the risk score delta, whether the risk class changed, and the full snapshot payloads for side-by-side comparison in the frontend.

7.6 Threat Intelligence Feed

The Feed page provides a paginated, searchable, filterable view of all investigated indicators. Filters include indicator type, risk class, and free-text search on the indicator value. Each row shows the indicator, type badge, risk badge, data source label, and investigation timestamp.

8.Intelligence Providers

ProviderAPISupported Indicator TypesData Extracted
VirusTotal v3 REST IPv4, IPv6, Domain, URL, MD5, SHA1, SHA256 Malicious / suspicious / harmless / undetected engine counts, total engines, reputation score, tags, categories, last analysis date
AlienVault OTX v1 REST IPv4, IPv6, Domain, URL, MD5, SHA1, SHA256 Pulse count and names, threat tags, malware family names, adversary attribution, ASN, country code, reputation

Both providers are configured via environment variables (VT_API_KEY, OTX_API_KEY). When unconfigured, the Settings page displays "Not configured" with setup instructions. Each adapter independently handles: rate limiting (HTTP 429), authentication errors (401), not-found (404), connection timeouts, and general exceptions — so one provider failing never blocks results from the other.

All provider requests are made server-side only. API keys are never exposed to the browser, logged to disk, or stored in the database.

9.Risk Scoring Methodology

The risk scoring module produces a numeric score from 0 to 100 using a weighted, capped factor model. Scores are then classified into four application-defined bands. If no provider returns usable data, the score is set to Insufficient Evidence rather than defaulting to zero.

10.Correlation Engine

The correlation engine compares normalised responses from all queried providers and outputs a structured correlation report. It identifies five possible agreement states:

StateConditionUI Presentation
agree_maliciousAll active sources flag the indicator as maliciousRed border panel with alert icon
agree_benignAll active sources return no malicious signalsGreen border panel with check icon
conflictSources disagree — at least one flags malicious, another does notAmber panel with warning icon and per-provider breakdown
single_sourceOnly one provider returned usable dataBlue panel with info icon noting reduced confidence
no_dataNo provider returned any usable dataGrey panel — score set to Insufficient Evidence

The engine also identifies overlapping evidence (tags reported by more than one source) and records each provider's specific finding when a conflict is detected. A narrative summary is generated in plain English. Absent records are never interpreted as confirmation of safety.

11.Recommendation Engine

The recommendation engine generates a prioritised, deduplicated list of analyst actions based on: the risk classification, the indicator type, the correlation agreement state, and which providers returned data. All recommendations are rule-based and deterministic — no AI model is used. Each recommendation includes a rationale and supporting evidence references.

Risk ClassIndicator TypeExample Recommendations
CriticalAnyEscalate immediately, isolate affected systems
Critical / HighIP / IPv6Block at perimeter firewall, review connection logs
Critical / HighDomainBlock DNS resolution, search proxy logs
Critical / HighHashScan endpoints for file hash, quarantine identified files
ModerateAnyMonitor closely, cross-reference with internal logs
LowAnyLog and monitor — no immediate action required
InsufficientAnyGather additional intelligence, manual investigation
Any (conflict)AnyManually review conflicting source findings
Any (missing providers)AnyConfigure missing intelligence sources
The recommendation engine is advisory only. It does not automatically block IPs, disable accounts, modify firewall rules, or take any disruptive action. The analyst remains in full control at all times.

15.Installation Guide

Requirements

  • Windows 10/11 (or Linux/macOS)
  • uv package manager (already installed at ~/.local/bin/uv)
  • Node.js 18+ (for frontend development / rebuilding only)
  • A modern browser (Chrome, Firefox, Edge)

Quick Start (One Step)

# From the project directory d:\SENTINEl-X
double-click  start.bat
# Server starts at http://localhost:5000 and browser opens automatically

Manual Start

# Backend (from d:\SENTINEl-X)
uv run python app.py
# → Server running at http://localhost:5000

# Frontend dev server (optional — only needed to edit frontend code)
cd frontend
npm run dev
# → Dev server at http://localhost:5173

# Tests
uv run python -m pytest test_sentinel_x.py -v

Environment Configuration

Copy .env.example to .env and fill in API keys to enable live intelligence queries:

VT_API_KEY=your_virustotal_api_key_here
OTX_API_KEY=your_alienvault_otx_api_key_here
DEMO_MODE=true
SECRET_KEY=change-this-to-a-random-64-char-string

18.Conclusion

SENTINEL-X 2.0 successfully delivers a complete, production-quality full-stack threat intelligence investigation platform meeting all 15 stated objectives. The application demonstrates practical application of cybersecurity engineering concepts including:

  • Multi-source intelligence correlation with explicit conflict detection and uncertainty disclosure
  • Explainable risk scoring where every contributing factor is visible to the analyst
  • Structured evidence management with database persistence, provenance tracking, and audit logging
  • Security-by-design with SSRF protection, input validation, SQL injection prevention, and rate limiting applied throughout
  • Full-stack engineering spanning React/TypeScript frontend, Python/Flask backend, and SQLAlchemy ORM

The platform is built on stable, widely-used technologies and follows established software engineering practices including separation of concerns, parameterised database queries, environment-based secret management, and a 47-test automated test suite. It is fully demonstrable offline through its 20-scenario demo mode, covering all risk classifications and indicator types without requiring any external API keys.

The primary differentiating features — the Correlation Engine's explicit conflict detection and the Explainable Risk Scoring module's factor-by-factor transparency — address a genuine gap in freely available threat intelligence tooling and demonstrate that automated security assessments can be made meaningfully interpretable to human analysts.
